# Windows 98 Explorer selection port

`src/m98shell_openfolder.c` supplies a four-argument, `WINAPI` implementation for the exact `SHOpenFolderAndSelectItems(pidl, 0, NULL, 0)` call made by Notepad++ 8.9.8 after `SHParseDisplayName` succeeds. The function is named `m98_SHOpenFolderAndSelectItems` for KernelEx registration. It takes the **absolute item PIDL**, resolves its existing filesystem path through the original Windows 98 `SHGetPathFromIDListA`, then dispatches the native Windows Explorer command `/select,"<path>"` with `ShellExecuteExA`. The command opens the item's parent and selects the item. The file path is quoted so the tested comma and space in a name are passed as one object. The wrapper uses the original Win98 `SEE_MASK_FLAG_DDEWAIT` (`SEE_MASK_NOASYNC`) to complete a possible DDE handoff before returning.

The [Microsoft API contract](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shopenfolderandselectitems) defines the `cidl == 0` interpretation and requires the caller to initialize COM. Archived [Microsoft Knowledge Base Q130510](https://jeffpar.github.io/kbarchive/kb/130/Q130510/) explicitly lists Windows 98 Second Edition and documents Explorer `/select,<item>` opening the parent and selecting the item. The pinned [Wine implementation](https://github.com/wine-mirror/wine/blob/df15af3652511150490934682202d45af892f887/dlls/shell32/shlfolder.c) splits the PIDL into parent and child, then sends private `WM_COPYDATA` data understood by Wine Explorer; that packet cannot be used with native Win98 Explorer. The pinned [ReactOS implementation](https://github.com/reactos/reactos/blob/9dc3ca87209fd8ebabd96c8ea95d439c13e7fdf8/dll/win32/shell32/shlfolder.cpp) also invokes Explorer `/select` for one item. Those two specific source files carry LGPL-2.1-or-later notices; this GPL-2.0-only file is a new implementation and copies no Wine or ReactOS code or data.

## Supported boundary

- `NULL` or empty item PIDL: `E_INVALIDARG`.
- Any `cidl > 0` or nonzero flags: `E_NOTIMPL`. The wrapper never claims to select only the first item from a larger request.
- PIDLs without an ordinary drive or UNC filesystem path: `E_NOTIMPL`. Missing files, missing Explorer, and launch failures return failing `HRESULT`s.
- `S_OK` means the Win98 Explorer selection command was accepted by `ShellExecuteExA`. A separate host shell-automation observation confirmed selection after the smoke returned. The guest direct smoke then returned exit 0 and `vm/select-shell3-guest.png` showed the named file focused in its parent Explorer folder.

The modern API's broader namespace, multiple selection, edit mode, and desktop selection behavior are outside this bounded port. Paths that cannot be represented through the guest ANSI code page, or that exceed `MAX_PATH`, need a separate implementation. The API contract requires COM initialization, which this focused wrapper assumes; it does not independently detect an uninitialized caller.

## Integration handoff

`src/m98shell.c` should declare `HRESULT WINAPI m98_SHOpenFolderAndSelectItems(LPCITEMIDLIST, UINT, LPCITEMIDLIST const *, DWORD);` and add `{"SHOpenFolderAndSelectItems", (unsigned long)m98_SHOpenFolderAndSelectItems}` to the KernelEx `SHELL32.DLL` name table between `SHCreateItemFromParsingName` and `SHParseDisplayName`. The table count becomes three. Both the development and release builds must compile `src/m98shell_openfolder.c` alongside `src/m98shell.c`, with the existing `-lshell32 -lole32 -lkernel32` libraries and PE32/4.10 flags. `integration/core.ini` must override `SHELL32.SHOpenFolderAndSelectItems=m98shell.0` in the active Win98 and compatibility profiles because pinned KernelEx currently routes that name to a stub. Its existing `SHParseDisplayName` overrides show the profiles and placement.

With the new function retained, the added DLL imports are `SHELL32.DLL!ShellExecuteExA` and `KERNEL32.DLL!GetFileAttributesA`, `GetLastError`, `GetWindowsDirectoryA`, `SetLastError`, `lstrcatA`, `lstrcpyA`, and `lstrlenA`. All are present in `benchmarks/win98se-ko-oem-native-exports-v1.json`. `tests/check_m98shell_pe98.py` must update its exact import map after integration; its native-export, relocation, and PE loader checks should remain in force. A static import probe must also require the third name through KernelEx rather than merely calling the standalone function.

## Evidence and next verification

The standalone `tests/m98shell_openfolder_smoke.c` was built as x86 PE32 with the Win98 target flags, linked directly with `src/m98shell_openfolder.c`, and passed on the Windows host. It tests null PIDL, a virtual My Computer PIDL, unsupported selection count and flags, a stale PIDL after deleting its file, and an existing temporary file named `target, one.txt`. The test leaves its unique temporary directory for inspection. In the host run, `Shell.Application.Windows()` reported the exact file selected in an Explorer window whose `LocationURL` was its parent folder. This verifies actual host selection for the comma-and-space case, beyond dispatch alone.

After integration, `build/m98shell.dll` passed the PE gate, `M98SELECT.EXE` direct smoke exited 0 in the disposable Win98 guest, and the Explorer screenshot showed the temporary `target, one.txt` selected. The rebuilt `SHELL_IMPORT_PROBE.EXE` had an ordinary named import for this function and exited 0 with PASS after the KernelEx `M98SHL3.DLL` route was activated. This is a separate result from Notepad++ behavior: the app reached the later `UXTHEME.DLL!DrawThemeTextEx` loader failure and did not start. The feature path in Notepad++ that calls this Shell function has not yet been exercised.
