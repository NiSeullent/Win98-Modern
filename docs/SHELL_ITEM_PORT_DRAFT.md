# SHELL32 parsing, `IShellItem`, and Explorer selection port

Notepad++ 8.9.8 x86 first stopped at missing `SHELL32.DLL!SHCreateItemFromParsingName` (`vm/npp-after-dwm-reloc.png`). After the KernelEx `m98shell.dll` API library was installed, its direct guest smoke and static-import probe passed; Notepad++ then stopped at missing `SHELL32.DLL!SHParseDisplayName` (`vm/npp-after-shell.png`). The same API library now supplies those names plus `SHOpenFolderAndSelectItems`. It is not a replacement `SHELL32.DLL`. `build.ps1` builds the library, direct behavior smokes, and a probe that statically imports all three names. `integration/core.ini` includes `m98shell` in `[DCFG1] contents` and routes `SHParseDisplayName` and `SHOpenFolderAndSelectItems` to it in the Windows 98, Me, and XP-compatible modes.

KernelEx's pinned [`core/apiconf.cpp`](../third_party/KernelEx/core/apiconf.cpp) merges named APIs from multiple listed API libraries for the same target module. Its existing [`kexbasen` SHELL32 table](../third_party/KernelEx/apilibs/kexbasen/shell32/_shell32_apilist.c) also lists `SHParseDisplayName`, but the default Windows 98 configuration explicitly erased it. The new route selects `m98shell.0`. The public Microsoft contracts for [SHCreateItemFromParsingName](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-shcreateitemfromparsingname) and [SHParseDisplayName](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shparsedisplayname), pinned Wine [`shellitem.c`](https://github.com/wine-mirror/wine/blob/df15af3652511150490934682202d45af892f887/dlls/shell32/shellitem.c) and [`pidl.c`](https://github.com/wine-mirror/wine/blob/df15af3652511150490934682202d45af892f887/dlls/shell32/pidl.c), and pinned ReactOS [`CShellItem.cpp`](https://github.com/reactos/reactos/blob/9dc3ca87209fd8ebabd96c8ea95d439c13e7fdf8/dll/win32/shell32/CShellItem.cpp) and [`wine/pidl.c`](https://github.com/reactos/reactos/blob/9dc3ca87209fd8ebabd96c8ea95d439c13e7fdf8/dll/win32/shell32/wine/pidl.c) informed the parse-to-PIDL design. The port uses the Windows 98 desktop `IShellFolder` and a new PIDL-backed `IShellItem` object. No Wine or ReactOS source was copied.

Implemented behavior: COM identity/reference ownership; `GetParent`; names returned with COM task allocator ownership; attributes delegated to the native Shell folder; default comparison; `BindToHandler` for `BHID_SFObject`, `BHID_SFUIObject`, and `BHID_DataObject`. `SHParseDisplayName` duplicates the const input before calling Win98's mutable `IShellFolder::ParseDisplayName`, forwards the optional bind context, passes an attribute mask only when an output is requested, and returns only requested true bits. The returned PIDL belongs to the caller and can be freed with `CoTaskMemFree`/`ILFree`; failure sets the PIDL to `NULL` and the optional attribute output to zero. The underlying `IShellFolder` has a `pchEaten` parameter, but public `SHParseDisplayName` does not, so this bridge passes `NULL` for it. Unsupported interfaces such as `IShellItem2`, other handlers, nonzero comparison hints, and URL names return errors. Filesystem path names are converted through the Windows 98 ANSI code page, so paths not representable in that code page are not yet covered. This is a partial `IShellItem` implementation, not general modern Shell coverage.

Current evidence: `build/m98shell.dll` passed `tests/check_m98shell_pe98.py`, including original Windows 98 native import and base-relocation checks. The gate confirmed `build/shell_import_probe.exe` is an x86 PE32 console 4.10 program with **named, non-delay imports** of all three SHELL32 functions. `build/m98shell_smoke.exe` passed host and guest direct calls for PIDL parsing, requested attribute mask, optional attribute output, invalid arguments, and the `IShellItem` methods. Its relative and absolute editing names matched the host's native `IShellItem` in the host run. The earlier two-export build passed the Windows 98 direct and static-import probes. After the three-export build was installed as the versioned `M98SHL3.DLL` and the installed `CORE.INI` was patched with only the required routes, the guest rebooted to the normal GUI. The new direct Shell smoke returned exit 0 with PASS. The new static-import probe returned exit 0 with `PASS: static SHELL32 parsing, item and Explorer selection imports`. The separate `M98SELECT.EXE` direct test returned exit 0, and `vm/select-shell3-guest.png` shows the requested `target, one.txt` selected in native Explorer. These results establish the focused guest path, not general Shell compatibility. Notepad++ still has **not** started; after the Shell routing it reached `UXTHEME.DLL!DrawThemeTextEx`.

## Guest verification sequence

1. On the host, run `./build.ps1`, then `./build/m98shell_smoke.exe` and `./build/shell_import_probe.exe`. Stage `build/m98shell.dll`, `build/m98shell_smoke.exe`, `build/shell_import_probe.exe`, and `integration/core.ini` in `vm/share`, and rebuild the Joliet test CD with `python tools/make_test_iso.py vm/share vm/test-media.iso`. Use the disposable `Win98Modern-Accel-128` VM only; shut it down before attaching the updated CD. Preserve `Win98Modern-Base`.
2. In the test guest, back up `C:\WINDOWS\KernelEx\CORE.INI`; copy the new `M98SHELL.DLL` beside that file. Preserve `[DCFG1] contents=std,kexbases,kexbasen,m98wrap,m98shell` and merge the three `SHELL32.SHParseDisplayName=m98shell.0` routes from `integration/core.ini` into the installed configuration, preserving other local settings. The repository file may be copied wholesale only if the installed file otherwise matches it. Restart Windows 98 so KernelEx reloads the API library table.
3. Run `m98shell_smoke.exe` from the test CD or a writable guest directory. Its PASS tests direct wrapper calls, PIDL ownership, attributes, and item names. Next run `shell_import_probe.exe`; its `PASS: static SHELL32 SHParseDisplayName and SHCreateItemFromParsingName imports` means the guest loader resolved both static names and the functions produced a PIDL, requested attributes, and an `IShellItem` file-system path. A loader dialog, crash, or FAIL must be recorded, not interpreted as success.
4. Re-run the same Notepad++ 8.9.8 x86 portable executable with its already tested app-local DBGHELP, DWMAPI, and BCRYPT shims. Record whether it starts or the exact next loader/runtime failure. A passing Shell probe by itself does not establish Notepad++ startup or broad Shell compatibility.
