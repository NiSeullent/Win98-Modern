# API porting and measurement

Consult `docs/VXKEX_SOURCE_AUDIT.md` when VxKex loader or API ideas are relevant. The audited VxKex mirror did not have a verified reuse license, so do not copy its code or binary into the public project without a license grant.

Inspect `src/m98wrap.c`, `src/kex_abi.h`, `THIRD_PARTY.md`, `tests/`, and the current import report first. KernelEx is pinned as a submodule; source snapshots for Wine and ReactOS are recorded in `THIRD_PARTY.md`. Read the exact relevant implementations from **both** projects before choosing a new wrapper, including its ABI, error behavior, concurrency, ownership, and dependencies. Leave a concise comment naming source paths/commits and explain any Win98-specific changes. Retain original copyright and LGPL/GPL notices where code or data is copied.

Use the catalogue-first campaign in `docs/API_PORTING_CAMPAIGN.md`. Rebuild `tools/index_api_sources.py` and `tools/build_porting_catalog.py` from pinned `porting/sources.json`, then select complete families from `build/api-catalog/work-queue.json`. Preserve every SDK candidate, COM/WinRT identity and overload, API-set alias, unresolved declaration and supplemental upstream export; no missing family may be silently excluded. Source declarations identify discovery locations, not working implementations. Inspect each chosen implementation body and dependency closure in both Wine and ReactOS, with relevant KernelEx/One-Core references, before reuse.

Implement common backends before dependent wrapper batches. Give agents disjoint family files and a shared ABI; reserve common provider tables and the guest VM for one integrator. Include sibling A/W/Ex, create/destroy, begin/complete, cancel/wait and teardown contracts in each batch. Application loader errors identify regressions and gaps within this complete plan rather than driving one missing function at a time. Treat timers, waits, I/O and cleanup groups as part of the threadpool backlog even after work-object APIs pass; treat thread/fiber teardown as part of FLS.

Have a different agent review object lifetime, callback reentry and failure cleanup before a checkpoint. Reproduce concrete races with controlled ordering and compare native Windows behavior: a test can contain its own scheduling assumption. Freeze implementation and probe hashes before guest validation. Pin supporting DLL hashes too; an old passing result does not validate a changed test fixture. Do not publish a lifecycle-dependent family merely because its isolated storage calls pass.

Use `remote/patch_core_wrapper_upgrade.py` to migrate the complete provider-owned route map across active profiles, then add reviewed families through `remote/patch_core_family.py`. Keep byte-preserved backups, table indices and a new provider filename. Confirm the guest desktop and remote-agent ready message before making the first host pipe request after cold boot. A request sent before the agent is ready can strand the VirtualBox serial connection and require a clean guest shutdown. Never count that transport failure as API evidence.

Do not import NT/Unix kernel behavior by name alone. Keep the KernelEx API table sorted, signatures and 32-bit calling conventions exact, and native imports present in the original Win98 SE DLLs. `build.ps1` runs the PE32/Windows 98 loader gate; update an import allowlist only after verifying the export in the pinned original-media manifest. Add meaningful success, failure, boundary, lifetime and thread cases to each family suite. Run host tests, then run the rebuilt DLL and static-import probe in the actual guest before claiming guest support. Pin provider and test hashes; a changed binary needs fresh evidence. Stub, forwarder, native-name presence and a successful DLL load are not behavioral completion.

For app probes, record the exact archive/version/hash, PE architecture, direct and delayed imports, first loader error, subsequent startup, and actual feature tests separately. An app-local DLL bridge such as `DBGHELP.DLL` belongs beside that app unless its guest behavior justifies system-wide installation. `docs/TARGET_APPS.md` names Chromium 150, Supermium, VLC, Notepad++, and VS Code. **All five actually running** in the installed guest, with reproducible functional checks, is a separate completion criterion. Do not substitute an older version without explicitly updating the agreed corpus. The current x64 VS Code image cannot load in 32-bit Win98 through API wrappers alone; record that architecture blocker until a real execution path exists.

The user's updated target is **100% of the defined Windows API surface**, including relevant Win32 exports and interface methods, not just the selected apps' import names. `docs/TARGET_APPS.md` pins SDK 10.0.28000.2705 as the intended inventory. Freeze and publish the denominator and exclusions before reporting a percentage. Label any older SDK or export-only inventory as a subset, and count an API as compatible only with appropriate guest behavioral evidence. Use `docs/PE_IMPORT_COVERAGE.md` for app triage, never as the whole-API denominator.
